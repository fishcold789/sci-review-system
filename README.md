## 它到底做什么

SCI Review System 是一套面向**理工科实验与工程领域综述章节**的 Codex Skill。它适合材料、机械、电气与电力、能源、土木、测量与检测、器件和制造工艺等方向。

它不是等你把文章写完以后再改几句话，也不是收到一个题目就直接生成一篇看似完整的综述。它会进入真实的科研过程，替你承担最耗时间的工作：清点材料、搜索文献、核对题录、精读原文、整理证据、建立分类、梳理技术演化、设计章节结构、起草正文、反复改稿和检查版本。

人的工作不是从白纸开始，而是判断一个已经成形的方案：这条分类轴对不对，这篇文献该不该放进来，这个判断值不值得保留，这一段是否需要删除。系统把每次选择、假设和推断摆出来，让你可以直接修改，而不是在一段流畅文字里猜它哪里出了问题。

一句话概括它的分工：

> AI 负责搜、下、读、归、总结和草拟，并在后台守住可检查的下限；人负责研究判断、文章取舍和最终验收。

## 什么时候接入都可以

它不要求所有项目从同一个起点开始。打开你的科研项目目录，手里有什么，就从什么位置接入。

| 你现在的状态 | 可以直接怎么说 | 系统首先交付什么 |
|---|---|---|
| 只有一个研究方向 | “我要写 X 方向的综述，这一节从哪里开始？” | 项目档案草案、缺失材料、定位与组织方案 |
| 已经找到一两篇高质量综述 | “以这两篇为范本，帮我判断分类轴怎么用。” | 范本分工、分类轴、反例检验和修改代价 |
| 手里有一批题录或 PDF | “清点这些文献，帮我筛选、归档并说明各自能支撑什么。” | 候选表、归档结果、证据卡和人话总结 |
| 已经有分类，但内部讲不顺 | “这几类方法之间到底是怎样演化的？” | 进化线、每一环的驱动问题和承重文献 |
| 已经有提纲或章节草稿 | “接着写这一节，先给我完整方案。” | 定位动词、推进链、逐段论点句和完整半成品 |
| 某一处反复改不明白 | “我还是没懂 X 和 Y 的区别。” | 从实际场景出发的六步讲解和可选判断 |
| 已经进入成稿期 | “按范本把这一节逐段雕刻到可以验收。” | 结构版本、分层修改版本、循环记录和验收结果 |
| 今天准备暂停 | “今天到这里，帮我收尾。” | 本轮确立与推翻的判断、改动文件和下一步 |

中途接入时，系统不会要求你把项目重新做一遍。它先读取项目档案和现有材料，判断哪些结论可以沿用、哪些环节缺输入，然后从最近的剧本继续。

## 核心工作方式

```mermaid
flowchart LR
    A["人给一句方向"] --> B["AI 清点项目并完成重活"]
    B --> C["交付完整半成品"]
    C --> D["人砍轴、改判断、定取舍"]
    D --> E["AI 重做并记录判断变化"]
    E --> F["后台检查证据、结构与版本"]
    F -->|继续修改| D
    F -->|满足停止条件| G["收官并沉淀项目记忆"]
```

这里的“半成品”不是半截文字，而是一份内容完整、可以被具体否定的版本。每次交付都应当说明：

1. 正文或方案本身；
2. 选择了什么，又排除了什么；
3. 依赖了哪些假设；
4. 哪些句子是 AI 根据现有信息推出来的；
5. 最值得人优先检查或删除的三处。

这样做的目的很简单：把人的工作从“凭空创作”变成“对具体方案做研究判断”。

## 一篇综述怎样完整跑下来

下面是一条从方向到成稿的完整路线。实际使用时可以从中间任意一步进入，也可以在某一步来回迭代。

### 0. 先建立项目档案

项目档案是技能在不同对话、不同阶段之间继续工作的长期记忆，放在**科研项目根目录**，不放在 Skill 仓库里。任何剧本开场都会先读它；没有档案，就先根据现有材料建立一份。

档案最少要明确四件事：

| 必填内容 | 它解决的问题 |
|---|---|
| 范本 | 学谁的分类、起笔、收尾或章节层级，并建立可量化的写作基线 |
| 下游工程判据 | 这篇综述最后要帮助读者判断哪个参数、边界或工程问题 |
| 禁止等价表 | 记录本领域那些“看起来能比，实际上条件不同”的概念和数字 |
| 分类轴 | 文章分几类、按什么判、跨界文献按什么优先级归属 |

档案还会持续记录各节进度、已经确立和已经推翻的判断、失败过的检索路径以及统计口径。项目暂停几天或换一个对话后，可以从这些记录继续，而不必重新解释全部背景。

模板见 [`templates/项目档案.md`](templates/项目档案.md)。

### 1. 找范本，先弄懂分类轴

系统先找 1–2 篇本领域公认写得好的综述，但不是把它们当作普通引用堆进文献库，而是明确每篇范本负责什么：分类、起笔与收尾，还是层级安排。

在沿用或修改一条分类轴之前，系统必须做一次反例检验：找出一个按表面理解应该进入 A 类、而范本实际放在 B 类的条目。找不到反例，只能沿用，不能声称已经读懂并改造了原轴。确实需要改轴时，还要写明改了什么、为什么改、放弃了原轴的什么能力，以及新轴在哪些文献上更难判断。

范本还会被量成数字：段数、段长、句长、从属密度、引文位置和段落节奏。这些数字只用来建立后续对标基线，不替代写作判断。

### 2. 把分类框变成技术进化线

分类只能说明“有哪些方法”，综述真正要讲清的是“为什么后来会出现下一种方法”。系统会为每一框建立一条进化线：

```text
原始需求
  → 方案 A 解决了什么
  → A 在什么物理场景下暴露局限
  → 方案 B 为什么因此出现
  → B 又带来了什么新代价
  → 目前仍未解决什么
```

每引入一篇承重文献，都要回答“它是被谁的什么局限逼出来的”。答不上来，就把它并入同类项，不让文章退化成逐篇罗列。系统还会回到范本引用的原始论文做二次学习，核对作者、题名、年份、图表和原文位置，避免只根据综述的转述继续转述。

模板见 [`templates/进化线表.md`](templates/进化线表.md)。

### 3. 检索、筛选和归档是一条支线

缺证据时，不必停下整篇文章重新做一次“大检索”。系统先清点本地库，再针对具体技术和具体场景并行检索，去重后交回候选表：题目、年份、一句话贡献、建议槽位、证据等级和推荐理由。

人只需要做两件事：勾选值得保留的论文，裁决边界条目。之后的下载、查重、首页身份核验、分类、命名、移动、哈希复核和台账登记由系统继续完成。

每个分类槽必须能判定新论文。系统会用三篇边界论文测试槽定义；有一篇判不动，就回到分类轴或进化线继续修，不靠“先放着”掩盖问题。模板见 [`templates/槽定义卡.md`](templates/槽定义卡.md)。

### 4. 文献入库时就变成可写的证据

每篇新论文归档后，同时生成两种结果：

- **证据卡**：它能支撑正文中的哪条主张，原文在第几页、哪张图或哪张表，结论在什么条件下成立，不能被外推到哪里；
- **人话总结**：先用清楚的中文说明做了什么、看到了什么、有什么限制，再附原文。英文原句负责作证，不负责替人讲懂。

证据不是按“这篇论文讲了什么”整理，而是按“它为整篇综述贡献了哪个陈述或判断”整理。证据不足时会登记缺口和当前允许使用的弱式写法；缺口没有清零，就不进入语言润色。

模板见 [`templates/证据卡.md`](templates/证据卡.md)。

### 5. 开工时一次交齐章节全家桶

开始写一节时，系统不会连续追问十几个问题，也不会只给一张空提纲。它先根据项目档案、范本、进化线和已有证据，交出一套可以直接修改的方案：

- **定位动词**：这一节到底是在界定、比较、解释、追踪还是判断；
- **组织轴**：按什么组织，排除了哪些看似合理的轴；
- **进化线**：每种方案为什么出现，又制造了什么新问题；
- **推进链**：整节怎样从第一步推到结论，哪里放关键判断，哪些内容明确不写；
- **逐段论点句**：每一段完成什么论证任务，由哪些文献承重。

推进链没有确定之前不急着切段。链条确定后，再按照范本的节奏建立分配表，把总词数换算成段数和句数，并让篇幅跟着论证重量走。模板见 [`templates/分配表.md`](templates/分配表.md)。

### 6. 先把结构刻对，再进入分层雕刻

改稿分为两个维度，顺序不能颠倒。

**维度一：结构。** AI 先给全量版本，人逐段点评：哪段固定、哪段删除、哪条判断不成立、哪里顺序不对。AI 按点评重做，并保存每版改动。这个阶段先把叙述模型刻出来，不为了字数指标过早压缩内容。

**维度二：对标。** 结构冻结后，才进入语言、节奏、结构复核、验收和收官等分层循环。每一轮只动一层，只生成一个新版本；每次修改后都回扫被改处，检查有没有解决旧问题却制造新问题。

循环开始时一次建立母本基准、约束文件、循环日志和后续轮次骨架。日志会追踪每轮改了什么、实测数据、方向是否正确、新问题、复发问题和未解决事项。同一问题复发三次，说明方法本身有漏洞，必须换一个独立上下文逐句检查，不能继续靠写作者自检。

完整开机骨架见 [`templates/循环开机.md`](templates/循环开机.md)。

### 7. 证据、文字和版本按固定顺序验收

验收不是最后统一“看起来不错”就结束，而是按下面的顺序进行：

1. 读原文并核对证据、条件、数字和禁止外推范围；
2. 根据核验结果修正论点，再冻结提纲；
3. 用分配表确定段落任务和篇幅；
4. 逐段落笔并检查每段承担的功能；
5. 对照范本测量段落、句子、从属关系和节奏；
6. 将提纲里的关键判断逐条定位回正文，防止改稿时误删；
7. 展开需要读者二次解码的抽象大词；
8. 需要压字数时先改表达方式，最后才考虑删论点；
9. 做忠实修改和自然表达两遍语言处理；
10. 中英对照核验主张、否定、因果、数字、单位、范围和引用；
11. 写盘后重新读取文件头尾，确认修改真正保存成功。

停止循环需要同时满足：硬门槛全部通过；只有少量区间偏离且写明理由；本轮没有新增复发问题；与基准逐段比较时没有新发现。收官时从各轮中择优确定英文版本，不默认最后一轮最好，再在不动英文科学含义的前提下生成清楚自然的中文版本。

### 8. 每轮结束都沉淀判断，而不是流水账

每次协作结束，系统会把本轮确立了什么、推翻了什么、改了哪些文件、还剩哪些待办，以及哪件事从模糊变成了可执行，写回项目档案。以后恢复项目时，读取的是一条可以追溯的判断链，而不是一堆聊天记录。

## 七个常用剧本

用户不需要记编号。下面这些日常说法会自动路由到对应工作方式。

| 剧本 | 什么时候用 | 主要交付 |
|---|---|---|
| A 开工全家桶 | 开始写、不会组织、刚接手一节 | 定位、组织轴、进化线、推进链、逐段论点句 |
| B 检索一条龙 | 缺证据、想找某类方法 | 去重候选表；人工勾选后继续下载、归档和登记 |
| C 入库即总结 | 新 PDF 入库、想快速了解一批论文 | 证据卡增量和按槽位整理的人话总结 |
| D 精读一篇 | 点名论文、进化线缺承重证据 | 全文与图表讲解、证据卡、进化线挂接 |
| E 雕刻循环 | 草稿“不对”、需要重写或进入成稿期 | 结构版本、分层对标版本、循环日志和验收 |
| F 思路沉淀 | 一轮讨论结束、准备暂停 | 确立/推翻的判断、文件变化、待办和里程碑 |
| G 破局讲解 | 概念不懂、两种方法分不清、同一处打转 | 场景化六步讲解，最后停在可供人裁决的选项上 |

详细规则见 [`references/06-剧本手册.md`](references/06-剧本手册.md)。

## 人和 AI 各自决定什么

AI 可以搜索、核对、统计、归纳、比较、提出方案和重做版本，但下面四类决定始终由人作出：

1. 一条材料是否成立、最终放在哪里；
2. 本节到底要完成什么，以及怎样才算写完；
3. 哪个判断值得占据篇幅；
4. 哪段、哪篇或哪条结论需要删除。

这不是形式上的“人在回路”，而是系统的工作边界。AI 可以把选择做成候选项、把代价讲明白，但不能把研究取舍伪装成自动化结果。

## 后台怎样保证它不只是一个漂亮提示词

Skill 在内部使用八级门禁。用户通常不需要亲自运行这些步骤，只有遇到阻断时系统才会说明卡在哪里。

| 级别 | 真正要通过的检查 |
|---|---|
| L1 找范本 | 能说清每篇范本具体负责什么 |
| L2 读懂轴 | 能用反例证明自己没有只读标题 |
| L3 进化线 | 每一环都能说明由什么物理场景逼出来 |
| L4 二次学习 | 题录与原始论文逐字核对 |
| L5 建槽 | 三篇边界论文都能按同一判据归类 |
| L6 读写法 | 明白每句承担什么功能、为什么需要这个长度 |
| L7 落笔 | 推进链先冻结，再按段落和层级循环写作 |
| L8 验收 | 机械检查完成，关键判断逐条回到正文定位 |

仓库还提供 6 个可以直接运行的检查器：

```powershell
python checks/check_emptiness.py 证据包.json
python checks/check_emptiness.py 稿件.md --text
python checks/check_ledger_vs_source.py 原文.pdf 台账.md
python checks/check_prose_discipline.py 范本.txt --measure
python checks/check_prose_discipline.py 稿件.md --baseline 母本基线.json
python checks/check_protected_spans.py 基线稿.md 候选稿.md
python checks/check_writeback.py 稿件.md --min-bytes 3000
python checks/audit_research_bundle.py 证据包.json
```

它们分别检查空话、题录与原文是否一致、稿件节奏、改写时引用/公式/图表号是否漂移、文件是否真正写入，以及证据包能否从正文追溯到来源。

检查结果只有三种：`PASS`、`BLOCK`、`NOT_CHECKED`。没有运行的检查必须如实标记为 `NOT_CHECKED`，不能因为省略就算作通过。需要模型判断的内容应当交给另一个上下文检查；写出文字的上下文不能给自己发合格证。

## 安装与使用

### 安装到 Codex

PowerShell：

```powershell
git clone https://github.com/fishcold789/sci-review-system.git "$HOME\.codex\skills\sci-review-system"
```

Bash：

```bash
git clone https://github.com/fishcold789/sci-review-system.git ~/.codex/skills/sci-review-system
```

仓库中的检查脚本不依赖第三方 Python 包，建议使用 Python 3.10 或更高版本。直接读取 PDF 题录时还需要系统能够调用 `pdftotext`；也可以先自行提取为 TXT 再检查。

安装完成后重新加载 Codex，在你自己的科研项目目录中调用 `$sci-review-system`。不要把论文、笔记、项目档案或生成的稿件写进 Skill 安装目录。

### 第一次使用

```text
使用 $sci-review-system 接手这个科研项目。
先读取现有材料，建立或补全项目档案，判断我现在卡在哪一步，
然后直接交付一个可以修改的完整半成品，并告诉我最应该先判断哪三处。
```

也可以直接说当前任务：

```text
使用 $sci-review-system，以这两篇综述为范本，帮我建立本章分类轴。
使用 $sci-review-system，搜索能够支撑“……”这条论点的论文，先给候选表。
```

## 适用范围与边界

当前版本聚焦于**理工科偏硬件、实验和工程问题的综述章节**。它不适合人文社科、纯数学或纯理论计算机方向，也不把投稿事务包装成“保证录用”。

系统不会编造论文、题录、数据、实验结果或来源。没有原文支撑的数字不会写进正文；检索不到合格文献时，“没有找到”本身就是可报告结果。账号登录、付费获取、版权确认以及最终科学判断仍由使用者负责。

## English Overview

SCI Review System is a Codex skill for developing evidence-grounded review chapters in experimental and engineering disciplines. It can join a project at any practical point: a rough direction, a pair of benchmark reviews, a PDF collection, an outline, a partial draft, or a section already undergoing revision.

The skill does not treat review writing as one long prompt. It keeps a project dossier, learns the organizing logic of benchmark reviews, reconstructs method evolution from source papers, searches for specific evidence gaps, turns each paper into claim-level evidence cards, and delivers a complete draft package before asking the researcher to judge it. Revision then proceeds in two stages: human-led structural sculpting followed by layer-specific comparison against a measured benchmark.

Seven playbooks cover the recurring work: section kickoff, literature search, ingestion summaries, single-paper close reading, revision loops, decision logging, and concept explanations. Eight quality gates and six deterministic checkers support the process in the background. Scientific scope, classification, value judgments, and deletion decisions remain with the researcher.

Install the repository under `~/.codex/skills/sci-review-system`, reload Codex, open your research project directory, and invoke `$sci-review-system` in ordinary language. See [`SKILL.md`](SKILL.md) for the operating rules and [`references/06-剧本手册.md`](references/06-剧本手册.md) for the complete playbooks.
